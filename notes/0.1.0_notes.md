# RapistOps Volume 0.1.0 Notes 

## Phase 1 - Core Data Model 

### 1.1 Source  
Definition: A source is the origin from which information is obtained by RapistOps. 

A source identifies where a piece of information came from and provides the context needed to trace that information back to its origin. 

#### Purpose 
The source object exists so RapistOps can preseve the origin of information rather than storing information without knowing where it came from. 

A source may provide one or many records. 

#### Examples 
A source may be: 
- A police report 
- A court 
- A prosecutor or district attorney office 
- A government database 
- A public records portal 
- A public website 
- A public document repository 
- An authorized API 
- An authorized data feed 
- A user-submitted source 

#### Source Responsibilities 
A source should allow RapistOps to identify: 
- What the source is 
- What organization or system operates the source 
- What type of source it is 
- Where the source can be accessed 
- Whether the source is publicly or otherwise lawfully accessible 
- The source's identifying information 

#### Source Fields 
The minimum Source model requires the following fields:

| Field | Purpose |
|---|---|
| "id" | Unique identifier for the Source within RapistOps |
| "name" | Human-readable name of the source |
| type | Classification of the Source |
| organization | Organization responsible for the Source, when applicable |
| location | Where the Source can be accessed |
| access_reference | Identifier or reference used to locate the Source within a larger system |

#### Decision
All six fields are required parts of the initial Source model.

These fields are considered the minimum information RapistOps needs to identify and locate a Source while preserving enough context for later provenance tracking.

No additional Source fields are being added at this stage.

#### Important Distinction 
A source represents the origin of information. A source does not determine whether the information is true, proven, or legally established. 

For example: 
- A police report can be a source. 
- The existence of that police report is a documented fact. 
- The allegations contained within the report are seperate information. 
- A later court outcome is seperate information. 

### 1.1 Provenance 
Definition: Provenance is the information RapistOps preserves about the origin, collection, history, and context of information stored in the system. 

#### Purpose 
Provenance allows RapistOps to answer: 
- Where did this information come from? 
- When was it obtained? 
- How was it obtained? 
- What source provided it? 
- What did the source contain at the time it was collected? 
- Has the information changed? 
- Can the information be traced back to its origin? 

#### Provenance Responsibilities 
Provenance should preserve information about: 
- Source 
- Collection date and time 
- Method of collection 
- Origional source location or identifier 
- Relevant source context 
- Collection history 
- Changes to the source or record over time 

#### Provenance Fields

Provenance answers:
**How did this particular information get into RapistOps?**

The minimum Provenance model requires the following fields:

| Field | Purpose |
|---|---|
| source_id | Identifies the Source associated with the information |
| collected_at | Records when RapistOps obtained the information |
| collection_method | Records how the information was obtained |
| source_reference | Identifies the specific item, page, document, record, or location within the Source |
| collection_context | Preserves relevant context about the information as it was collected |

#### Field Definitions

##### source_id

Connects the Provenance record to the Source from which the information originated.

##### collected_at

Records the date and time RapistOps obtained the information.

##### collection_method

Records how the information was obtained.

Examples may include:

- API
- Document import
- Authorized web collection
- Manual entry
- User submission
- Authorized data feed

##### source_reference

Identifies the specific origin of the information within the Source.

This may be a:

- URL
- Document identifier
- Record identifier
- Page
- Database reference
- Other source-specific identifier

##### collection_context

Preserves relevant contextual information about the information at the time it was collected.

This prevents important collection context from being lost during ingestion or later processing.

#### Decision

The initial Provenance model contains five fields:

- `source_id`
- `collected_at`
- `collection_method`
- `source_reference`
- `collection_context`

No additional Provenance fields are being added at this stage.

#### Core Principle

Provenance establishes traceability.

It does not establish the truth of the information itself.

#### Important Distinction 
Provenance does not establish the truth of information. It establishes the traceability of information. 

A record can therefore preseerve: 
1. What information was found 
2. Where it was found 
3. When it was found 
4. How it was obtained 
5. What source provided it 

Without automatically treating the information as independently verified facts. 

### Relationship Between Source and Provenance 

A source answers: **Where did this information come from?**

Provenance answers: **How can we trace this information back to where it came from and understand its history?**

A source is therefore part of the provenance of information, but provenance contains additional information about collection and history. 

### Core Principle 
**Every externally obtained record should be traceable to its source and collection context.**

### 1.2 Record
Definition: A Record is a structured representation of information obtained from a Source and stored by RapistOps.

A Record represents a distinct piece of documented information that RapistOps has collected, preserved, and structured.

#### Purpose
The Record object exists so RapistOps can represent information obtained from sources in a consistent structure rather than treating every source as unstructured information.

A Source may provide one or many Records.

A Record may describe a person, event, case, institution, report, proceeding, outcome, or other documented information.

#### Examples
A Record may represent:
- A police report
- A court filing
- A court proceeding
- A charging document
- A case record
- A public institutional record
- A government record
- A public document
- A documented report or allegation
- A documented outcome
- Other structured information obtained from a Source

#### Record Responsibilities
A Record should allow RapistOps to identify:
- What the record is
- What type of record it is
- Which Source provided it
- When it was created or published, when known
- When it was collected by RapistOps
- What information the record contains
- Which entities or events the record relates to
- The record's identifying information

#### Record Fields
The minimum Record model requires the following fields:
    | Field | Purpose |
    |---|---|
    | id | Unique identifier for the Record within RapistOps |
    | source_id | Identifies the Source that provided the Record |
    | provenance_id | Connects the Record to its Provenance information |
    | type | Classification of the Record |
    | title | Human-readable title or name of the Record |
    | source_reference | Identifies the specific Record within the Source |
    | created_at | Date and time the Record was created, when known |
    | published_at | Date and time the Record was published, when known |
    | collected_at | Date and time RapistOps obtained the Record |

#### Decision
All nine fields are required parts of the initial Record model.

These fields are considered the minimum information RapistOps needs to identify, classify, locate, and contextualize a Record while maintaining its connection to its Source and Provenance.

No additional Record fields are being added at this stage.

#### Important Distinction
A Record represents documented information.

A Record does not automatically establish that every statement contained within it is true, independently verified, or legally established.

For example:
- A police report is a Record.
- The existence of the police report is a documented fact.
- Statements or allegations contained within the report are information contained in that Record.
- A later court outcome is a separate Record or documented outcome.

A Record should preserve what was documented without automatically transforming documentation into established fact.

### 1.2 Evidence
Definition: Evidence is information, material, or documentation that supports, describes, or provides context for a claim, event, person, case, or other Record represented by RapistOps.

Evidence represents the material that can be examined in relation to information stored in the system.

#### Purpose
The Evidence object exists so RapistOps can distinguish the existence of a Record from the material or information that supports, documents, or provides context for what the Record describes.

Evidence may be associated with one or many Records.

A Record may have one or many pieces of Evidence.

#### Examples
Evidence may include:
- Documents
- Reports
- Court filings
- Public records
- Statements
- Images
- Videos
- Audio recordings
- Other documented materials
- User-submitted materials
- Other lawfully accessible information

#### Evidence Responsibilities
Evidence should allow RapistOps to identify:
- What the evidence is
- What type of evidence it is
- Where it came from
- Which Record or Records it relates to
- When it was obtained
- How it was obtained
- The evidence's identifying information
- Relevant contextual information

#### Evidence Fields
The minimum Evidence model requires the following fields:
    | Field | Purpose |
    |---|---|
    | id | Unique identifier for the Evidence within RapistOps |
    | type | Classification of the Evidence |
    | source_id | Identifies the Source associated with the Evidence |
    | provenance_id | Connects the Evidence to its Provenance information |
    | record_id | Identifies the Record or primary Record associated with the Evidence |
    | reference | Identifies or locates the specific Evidence |
    | description | Describes what the Evidence represents |

#### Decision
All seven fields are required parts of the initial Evidence model.

These fields are considered the minimum information RapistOps needs to identify Evidence, connect it to its origin and associated Record, and describe what it represents.

No additional Evidence fields are being added at this stage.

#### Important Distinction
Evidence does not automatically establish the truth of a claim.

Evidence is something that can be examined in relation to a claim, Record, event, case, or other information.

RapistOps must preserve the distinction between:
- The existence of Evidence
- What the Evidence contains
- What a Source claims
- What a Record documents
- What has been independently verified
- What has been legally established

#### Core Principle
**Evidence should remain traceable to its origin and context.**

RapistOps should preserve Evidence without automatically assigning conclusions that the Evidence itself does not establish.

### Relationship Between Record and Evidence
A Record answers: **What documented information does RapistOps represent?**

Evidence answers: **What material or information supports, documents, or provides context for that Record?**

A Record and Evidence are therefore related but distinct concepts.

A Record represents structured documented information.

Evidence represents material that can be examined in relation to that information.

### Core Principle
**Records preserve documented information. Evidence preserves the material and context that can be examined in relation to that information.**

### 1.3 Person
Definition: A Person is an individual represented by information stored in RapistOps.

A Person represents an individual who may appear in one or many Records, Events, Cases, Institutions, or Relationships.

#### Purpose
The Person object exists so RapistOps can represent individuals as distinct entities rather than treating every appearance of a person's name as an unrelated piece of information.

A Person may appear in many Records. A Person may have different roles in different Records or Cases.

#### Examples
A Person may be:
- A survivor
- A victim
- A reporting person
- A reported person
- An accused person
- A charged person
- A convicted person
- A witness
- An investigator
- A prosecutor
- An attorney
- An institutional employee
- Another participant documented in a Record

#### Person Responsibilities
A Person should allow RapistOps to identify:
- The individual represented by the Person entity
- Names or identifiers associated with the individual
- Information needed to distinguish the individual from other people
- Relationships to Records
- Relationships to Events
- Relationships to Cases
- Relationships to Institutions
- The person's documented roles within specific contexts

#### Person Fields
The minimum Person model requires the following fields:
    | Field | Purpose |
    |---|---|
    | id | Unique identifier for the Person within RapistOps |
    | name | Name associated with the Person |
    | identifiers | Other identifiers used to distinguish or reference the Person |
    | description | Contextual information about the Person |
    | created_at | Date and time the Person entity was created in RapistOps |
    | updated_at | Date and time the Person entity was last updated |

#### Decision
All six fields are required parts of the initial Person model.

These fields are considered the minimum information RapistOps needs to represent an individual and maintain that individual's identity across related records.

No additional Person fields are being added at this stage.

#### Important Distinction
A Person's existence as an entity in RapistOps does not establish any particular allegation, role, or outcome.

A Person may have different documented roles in different Records or Cases.

For example:
- A person may be identified as a witness in one Record.
- The same person may appear as an institutional employee in another Record.
- A person appearing in a report does not automatically establish the claims made about them.
- A person appearing in RapistOps does not automatically mean that the person committed an offense.

Roles and claims must remain connected to the specific Records, Events, Cases, or Relationships that document them.

### 1.3 Institution
Definition: An Institution is an organization, agency, system, or other organizational entity represented by information stored in RapistOps.

An Institution represents an organization that may create, maintain, receive, investigate, process, publish, or otherwise be connected to Records, Events, Cases, People, or other entities.

#### Purpose
The Institution object exists so RapistOps can represent organizations as distinct entities rather than treating every organizational reference as unstructured text.

An Institution may be connected to many Records, People, Events, and Cases.

#### Examples
An Institution may be:
- A police department
- A court
- A prosecutor or district attorney office
- A school
- A university
- A government agency
- An employer
- An organization
- A public records system
- Another institution documented in a Record

#### Institution Responsibilities
An Institution should allow RapistOps to identify:
- What the Institution is
- The Institution's name
- The type of Institution
- The jurisdiction or organizational context of the Institution
- Records associated with the Institution
- People associated with the Institution
- Events associated with the Institution
- Cases associated with the Institution

#### Institution Fields
The minimum Institution model requires the following fields:
    | Field | Purpose |
    |---|---|
    | id | Unique identifier for the Institution within RapistOps |
    | name | Human-readable name of the Institution |
    | type | Classification of the Institution |
    | jurisdiction | Jurisdiction or organizational context associated with the Institution |
    | location | Geographic or access location associated with the Institution |
    | description | Contextual information about the Institution |
    | created_at | Date and time the Institution entity was created in RapistOps |
    | updated_at | Date and time the Institution entity was last updated |

#### Decision
All eight fields are required parts of the initial Institution model.

These fields are considered the minimum information RapistOps needs to represent an organization and distinguish it from other institutions.

No additional Institution fields are being added at this stage.

#### Important Distinction
An Institution's appearance in RapistOps does not automatically establish responsibility, wrongdoing, negligence, or any other conclusion about that Institution.

An Institution represents an organizational entity and its documented relationships to Records, People, Events, Cases, or other entities.

### Relationship Between People and Institutions
A Person answers: **Who is the individual represented by this information?**

An Institution answers: **What organization or organizational entity is represented by this information?**

People and Institutions can be connected through documented relationships.

For example:
- A Person may work for an Institution.
- An Institution may investigate an Event.
- An Institution may create or maintain a Record.
- An Institution may be involved in a Case.
- A Person may interact with an Institution during an investigation or proceeding.

These relationships should be represented explicitly rather than being assumed from a person's name or an Institution's appearance in a Record.

### Core Principle
**People and Institutions are entities; their roles, actions, and relationships must be represented through documented context rather than inferred from existence alone.**

### 1.4 Event
Definition: An Event is a documented occurrence represented by information stored in RapistOps.

An Event represents something that happened or is documented as having happened at a particular point or period in time.

An Event may involve one or many People, Institutions, Records, or Cases.

#### Purpose
The Event object exists so RapistOps can represent occurrences independently from the Records that document them.

Multiple Records may describe the same Event.

An Event allows RapistOps to connect information from different sources that refers to the same documented occurrence.

#### Examples
An Event may be:
- A reported incident
- An investigation
- An arrest
- A charging event
- A court proceeding
- A hearing
- A sentencing
- An institutional action
- Another documented occurrence

#### Event Responsibilities
An Event should allow RapistOps to identify:
- What the Event represents
- What type of Event it is
- When the Event occurred, when known
- Where the Event occurred, when known
- Which People were associated with the Event
- Which Institutions were associated with the Event
- Which Records document the Event
- Which Case the Event belongs to, when applicable

#### Event Fields
The minimum Event model requires the following fields:
    | Field | Purpose |
    |---|---|
    | id | Unique identifier for the Event within RapistOps |
    | type | Classification of the Event |
    | title | Human-readable name or description of the Event |
    | occurred_at | Date and time the Event occurred, when known |
    | location | Location associated with the Event, when known |
    | description | Contextual information describing the Event |

#### Decision
All six fields are required parts of the initial Event model.

These fields are considered the minimum information RapistOps needs to represent a documented occurrence and provide basic temporal, geographic, and descriptive context.

No additional Event fields are being added at this stage.

#### Important Distinction
An Event represents a documented occurrence.

The existence of an Event entity does not automatically establish every claim associated with that Event as independently verified fact.

When the timing, location, or details of an Event are uncertain, RapistOps must preserve that uncertainty rather than inventing precision.

### 1.4 Case
Definition: A Case is a structured representation of a legal, investigative, institutional, or other formal matter represented by information stored in RapistOps.

A Case provides an organizational structure for Records, Events, People, Institutions, Evidence, and Outcomes associated with a particular matter.

#### Purpose
The Case object exists so RapistOps can group and connect information belonging to the same documented matter.

A Case may contain many Records and Events. A Case may involve many People and Institutions. A Case may have one or many documented outcomes or status changes over time.

#### Examples
A Case may be:
- A criminal case
- A civil case
- An investigation
- An institutional proceeding
- An administrative matter
- Another formally documented matter

#### Case Responsibilities
A Case should allow RapistOps to identify:
- What the Case represents
- What type of Case it is
- The Case's identifying information
- Which People are associated with the Case
- Which Institutions are associated with the Case
- Which Events belong to the Case
- Which Records document the Case
- Which Evidence is associated with the Case
- What documented outcomes are associated with the Case

#### Case Fields
The minimum Case model requires the following fields:
    | Field | Purpose |
    |---|---|
    | id | Unique identifier for the Case within RapistOps |
    | type | Classification of the Case |
    | name | Human-readable name or title of the Case |
    | identifier | Official or source-specific Case identifier, when available |
    | description | Contextual information describing the Case |
    | opened_at | Date and time the Case was opened or initiated, when known |
    | closed_at | Date and time the Case was closed or concluded, when known |

#### Decision
All seven fields are required parts of the initial Case model.

These fields are considered the minimum information RapistOps needs to identify and organize a documented matter while allowing its associated Records, Events, People, Institutions, and outcomes to be connected.

No additional Case fields are being added at this stage.

#### Important Distinction
A Case represents a documented matter.

The existence of a Case does not establish guilt, responsibility, wrongdoing, or any other legal conclusion.

A Case may exist without a conviction or other particular outcome.

The system must preserve the Case and its documented history regardless of whether the matter results in prosecution, dismissal, acquittal, conviction, or another outcome.

### Relationship Between Events and Cases
An Event answers: **What documented occurrence happened, and when?**

A Case answers: **What documented matter organizes the related Records, Events, People, Institutions, and outcomes?**

A Case may contain many Events.

An Event may belong to a Case, but not every Event must belong to a Case.

Multiple Records may document the same Event.

Multiple Events may belong to the same Case.

### Core Principle
**Events represent documented occurrences; Cases organize the larger documented matters to which those occurrences belong.**

### 1.5 Status
Definition: A Status represents the documented state or outcome associated with a Record, Case, Event, or other entity in RapistOps.

A Status describes what is documented about the state of a matter at a particular point in time.

#### Purpose
The Status object exists so RapistOps can represent different stages and outcomes without collapsing them into a single interpretation.

Status allows the system to distinguish between:
- A report existing
- An investigation occurring
- Charges being filed
- A prosecution occurring
- A case being dismissed
- An acquittal occurring
- A conviction occurring
- Other documented outcomes

#### Examples
A Status may represent:
- Reported
- Investigated
- Charged
- Prosecuted
- Dismissed
- Acquitted
- Convicted
- Pending
- Closed
- Other documented states or outcomes

#### Status Responsibilities
A Status should allow RapistOps to identify:
- What status is being represented
- What entity the status applies to
- When the status became applicable
- Whether the status represents a current state or historical state
- What Record or Source documents the status
- Relevant context surrounding the status

#### Status Fields
The minimum Status model requires the following fields:
    | Field | Purpose |
    |---|---|
    | id | Unique identifier for the Status within RapistOps |
    | type | Classification of the Status |
    | entity_id | Identifies the entity the Status applies to |
    | effective_at | Date and time the Status became applicable, when known |
    | source_id | Identifies the Source documenting the Status |
    | record_id | Identifies the Record documenting the Status |
    | description | Contextual information about the Status |

#### Decision
All seven fields are required parts of the initial Status model.

These fields are considered the minimum information RapistOps needs to represent a documented state or outcome, identify what it applies to, and preserve the source and Record supporting that Status.

No additional Status fields are being added at this stage.

#### Important Distinction
A Status represents a documented state or outcome.

A Status does not automatically describe the complete truth of a situation.

For example:
- Reported means that a report exists.
- Investigated means that an investigation is documented.
- Charged means that charges are documented.
- Dismissed means that a dismissal is documented.
- Acquitted means that an acquittal is documented.
- Convicted means that a conviction is documented.

These statuses must remain distinct.

The existence of one Status must not automatically imply another Status.

For example:
- Reported does not mean convicted.
- Investigated does not mean charged.
- Charged does not mean convicted.
- Dismissed does not mean that the underlying report never existed.
- Acquitted does not mean that no report or investigation existed.

#### Status History
RapistOps must preserve Status changes over time rather than silently replacing previous states.

For example, a Case may have a documented progression such as:
    Reported
    Investigated
    Charged
    Prosecuted
    Convicted

Another Case may have a different documented progression:
    Reported
    Investigated
    Dismissed

Another may be:
    Reported
    Investigated
    Charged
    Acquitted

The system must preserve the documented history rather than treating the final Status as the only information that matters.

### Relationship Between Status and Records
A Status should be traceable to the Record or Records that document it.

A Status should therefore not exist as an unsupported assertion.

The system should be capable of answering: **What source and Record support this Status?**

### Core Principle
**Status represents documented state and outcome, not an interpretation of guilt, innocence, truth, or responsibility.**

RapistOps must preserve the distinction between what was reported, what was investigated, what was legally pursued, and what outcome was documented.

### 1.6 Relationship
Definition: A Relationship represents a documented connection between two or more entities represented in RapistOps.

A Relationship allows RapistOps to explicitly represent how People, Records, Evidence, Events, Cases, Institutions, Sources, and other entities are connected.

#### Purpose
The Relationship object exists so RapistOps can connect information without requiring those connections to be inferred from unstructured text alone.

Relationships allow the system to represent connections across different sources and entities while preserving the context in which the connection exists.

A Relationship may connect entities of the same type or different types.

#### Examples
A Relationship may represent:
- A Person is associated with a Case
- A Person is associated with an Event
- A Person is associated with an Institution
- An Institution is associated with a Case
- A Record documents an Event
- A Record documents a Case
- A Record references a Person
- Evidence supports or documents a Record
- A Case contains an Event
- A Source provides a Record
- A Record is related to another Record

#### Relationship Responsibilities
A Relationship should allow RapistOps to identify:
- What entities are connected
- What type of relationship exists
- The direction of the relationship, when applicable
- When the relationship became applicable, when known
- What Source or Record documents the relationship
- Relevant context surrounding the relationship
- Whether the relationship is current or historical

#### Relationship Fields
The minimum Relationship model requires the following fields:
    | Field | Purpose |
    |---|---|
    | id | Unique identifier for the Relationship within RapistOps |
    | source_entity_id | Identifies the originating entity in the Relationship |
    | target_entity_id | Identifies the entity connected to the originating entity |
    | type | Classification of the Relationship |
    | source_id | Identifies the Source documenting the Relationship |
    | record_id | Identifies the Record documenting the Relationship |
    | effective_at | Date and time the Relationship became applicable, when known |
    | description | Contextual information describing the Relationship |

#### Decision
All eight fields are required parts of the initial Relationship model.

These fields are considered the minimum information RapistOps needs to represent an explicit connection between entities while preserving the Source, Record, timing, and context supporting that connection.

No additional Relationship fields are being added at this stage.

#### Important Distinction
A Relationship represents a documented connection.

A Relationship does not automatically establish the truth, intent, responsibility, or meaning of that connection beyond what is documented.

For example:
- A Record may identify a Person as an employee of an Institution.
- A Record may state that a Person was investigated.
- A Record may connect an Event to a Case.
- A Record may identify an Institution as participating in a proceeding.

The existence of the Relationship does not allow RapistOps to infer additional conclusions that are not documented.

#### Relationship Direction
Relationships may be directional.

For example:
    Person -> associated_with -> Case
    Institution -> investigated -> Event
    Record -> documents -> Event
    Source -> provides -> Record

Some relationships may be conceptually bidirectional even when stored as a directed connection.

For example:
    Person -> associated_with -> Case
    Case -> associated_with -> Person

The system should preserve the relationship type rather than relying only on the existence of a connection.

#### Relationship History
Relationships may change over time.

RapistOps should preserve historical relationships rather than silently replacing them.

For example:
    Person -> employed_by -> Institution

may later become:
    Person -> formerly_employed_by -> Institution

The historical relationship should remain traceable when supported by documented information.

#### Relationship and Evidence
Relationships should be traceable to the information that supports them.

A Relationship should therefore be capable of answering: **What Source or Record documents this connection?**

This prevents relationships from becoming unsupported assumptions generated solely from matching names or other similarities.

### Relationship Between Entities
A Relationship answers: **How are these entities connected according to documented information?**

The entities themselves answer: **What things exist in the system?**

For example:
    Person
    Relationship
    Case

The Person and Case are entities.

The Relationship explains the documented connection between them.

### Core Principle
**Relationships connect entities; they do not manufacture conclusions.**

Every meaningful relationship should be traceable to the Record, Evidence, Source, or other documented information that supports the connection.
